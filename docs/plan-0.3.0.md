# ddashboard 0.3.0 계획: 대시보드로 꾸리는 개발 팀

## 목표

- **마스터(사용자)는 팀장하고만 협업**합니다. 팀장은 여러 명일 수 있습니다.
- **팀원 세션은 역할을 맡습니다.** 예: 기획, 프론트, 백엔드, QA.
- 팀원은 작업이 끝나면 **팀장에게 보고**합니다.
- 팀장은 특이사항, 수정사항, 마스터가 알아야 할 것, 검수 요청만 **대시보드에 올립니다.**
- **토큰 사용량을 측정하면서 설계를 정합니다.** 추측으로 정하지 않습니다.

## 핵심 원칙 (지금까지 배운 것)

1. **비용은 "깨우는 횟수 × 깨어난 세션의 맥락 크기"로 정해집니다.** 0.1.0 분석에서 팀장 맥락이 턴당 평균 37.5만 토큰이었고, 이것이 비용의 대부분이었습니다.
2. **전달 자체는 공짜로 만들 수 있습니다.** 파일 인박스와 대기 명령은 토큰 0입니다. 그래서 줄여야 할 것은 "누가, 몇 번, 얼마나 큰 맥락으로 깨어나는가"입니다.
3. **작은 일은 팀장이 직접, 큰 일만 분배합니다.** 팀원을 새로 띄우면 저장소를 다시 읽는 비용이 붙습니다.

## 단계별 계획

### 1단계: 측정 도구 (연구의 바탕)

토큰을 재지 않으면 연구가 안 되므로 가장 먼저 만듭니다.

- **세션별 토큰 미터:** Stop 훅이 transcript 끝부분에서 이번 턴의 사용량(입력, 캐시 읽기, 캐시 쓰기, 출력)을 읽어 기록합니다. 모델 토큰은 0입니다.
- **깨운 원인 기록:** 사람 입력, 대시보드 답글, 팀원 보고, 팀장 지시 중 무엇 때문에 깨어났는지 함께 기록합니다.
- **대시보드 표시:** 사이드바 세션마다 누적 토큰과 최근 맥락 크기를 표시하고, 팀 전체 합계를 보여 줍니다. 맥락이 커지면 경고합니다.

### 2단계: 역할과 통신

- **팀장 등록:** `/ddashboard:dashboard lead 백엔드팀장` 처럼 이름을 붙여 켭니다.
- **팀원 등록:** 팀장이 팀원을 띄울 때 지시문 첫 줄에 `[ddash role=프론트 lead=<팀장 세션 ID>]` 태그를 넣으면, 첫 입력 때 훅이 소속과 역할을 등록합니다. Orca를 쓰든 터미널에 직접 붙여 넣든 동작합니다.
- **통신은 ddashboard 인박스로 통일합니다.** Orca 없이도 동작하고 토큰 0입니다.
  - 팀장 → 팀원: 팀원 인박스에 지시를 넣습니다.
  - 팀원 → 팀장: 팀원의 카드는 대시보드 본문이 아니라 팀장 인박스로 갑니다.
  - 팀장 → 대시보드: 팀장 카드만 본문에 올라갑니다.
  - 마스터 답글: 팀장 카드에만 달 수 있고, 팀장에게 갑니다.
- **화면:** 사이드바에 팀장 아래로 팀원이 역할과 함께 들여쓰기로 표시됩니다. 팀원 보고는 팀장 카드 안에 접어서 볼 수 있습니다.

### 3단계: 팀장 비용을 줄이는 장치

- **보고 묶어 받기:** 팀원 보고가 연달아 오면 몇 초 기다렸다가 한 번에 받습니다. 깨우는 횟수가 줄어듭니다.
- **보고는 짧게, 근거는 파일로:** 보고는 카드 JSON(요약 3줄, 확인할 것)만 보냅니다. 긴 내용은 파일로 남기고 경로만 전달해서, 팀장이 필요할 때만 읽게 합니다.
- **팀장 맥락 상한과 교대:** 맥락이 일정 크기(예: 15만 토큰)를 넘으면 팀장이 인수인계 문서를 쓰고 새 팀장 세션으로 교대합니다. 1단계 미터가 신호를 줍니다.
- **작업 키:** 카드에 작업 이름(key)을 붙이고, 같은 key의 새 카드가 오면 이전 카드를 대체합니다. 진행 중 카드가 완료 카드로 자연스럽게 바뀝니다.
- **카드 언어 설정:** 프로젝트별로 카드 언어를 정합니다. 팀원에게 영어로 지시해도 카드는 마스터의 언어로 나옵니다.
- **응답 없는 세션 표시:** 대기 명령도 없고 오래 조용한 세션은 "응답 없음"으로 표시합니다.

### 4단계: 실험

같은 과제를 세 가지 방식으로 돌려 토큰, 걸린 시간, 결과 품질을 비교합니다.

| 방식 | 내용 |
|---|---|
| A. 혼자 | 세션 하나가 전부 처리 |
| B. 직접 보고 | 여러 세션이 각자 대시보드에 보고 (0.2.0 방식) |
| C. 팀장 경유 | 팀장 + 역할 팀원, 보고는 팀장에게 (0.3.0 방식) |

과제는 이 저장소의 실제 기능 하나로 정합니다. 결과로 기본값(보고 묶음 시간, 맥락 상한, 팀원 모델 등급)을 정하고, 문서로 남깁니다.

## 모드: solo / team (자유도를 지키는 구조)

도구는 장치만 제공하고, 일하는 방식은 사용자가 고릅니다. 개발론은 강제하지 않고 team 모드의 기본값과 README의 안내로 제공합니다.

| | solo (기본) | team |
|---|---|---|
| 켜는 법 | `/ddashboard:dashboard` | `/ddashboard:dashboard team <팀장 이름>` |
| 누가 대시보드에 올리나 | 연결된 모든 세션 (0.2.0과 같음) | 팀장만. 팀원 카드는 팀장 인박스로 |
| 마스터 답글 | 카드를 올린 세션으로 | 팀장에게 |
| 팀원 등록 | 없음 | 팀장이 띄울 때 태그로 소속·역할 등록 |
| 규칙 조정 | — | 프로젝트 설정 파일에서 규칙별로 켜고 끔 (예: QA 카드는 직접 게시, 팀원끼리 대화 허용) |

- 모드는 프로젝트마다 다르게 둘 수 있고, 언제든 바꿀 수 있습니다.
- **전환 방법은 두 가지 모두 지원합니다(확정).** 명령어(`/ddashboard:dashboard team <팀장 이름>` / `solo`)와 대시보드 화면(사이드바 프로젝트 이름 옆 solo/team 전환, team 선택 시 팀장 세션 고르기).
- 전달 경로는 전환 즉시 바뀝니다(훅·서버 처리, 토큰 0). 세션 안내문은 다음 입력 때 한 번만 새 모드로 다시 넣습니다.
- team 모드에서 팀장이 종료되면 팀원 카드는 대시보드에 직접 올리고 "팀장 없음" 경고를 표시합니다.
- README에 두 모드의 사용법을 나눠 안내하고, team 모드의 권장 방식(개발론)은 별도 가이드 문서로 링크합니다.

## 마스터 피드백 반영 (2026-11-25)

1. **저장소 압축(프로젝트 브리프):** 팀원이 매번 저장소를 탐색하지 않도록, 팀장이 `프로젝트 브리프`(구조, 파일별 한 줄 설명, 규칙, 현재 작업 상태)를 만들어 둡니다.
   - 팀원은 탐색 대신 브리프를 읽고 필요한 파일만 엽니다. 탐색 수만 토큰 → 브리프 수천 토큰.
   - **브리프를 모든 팀원 맥락의 같은 위치에 같은 내용으로 넣으면 프롬프트 캐시가 세션 사이에서 공유됩니다.** 두 번째 팀원부터는 브리프 비용이 캐시 읽기(약 1/10)로 떨어집니다.
   - git HEAD가 브리프 작성 시점보다 많이 앞서면 훅이 "브리프 갱신 필요"를 팀장에게 알립니다.
   - 팀원 수명은 "작업마다 새로 + 브리프"를 기본으로 하고, 실험에서 "역할별 유지 + 맥락 상한"과 비교합니다.
2. **팀원끼리 직접 대화의 낭비 위험:** 두 세션이 끝없이 주고받는 핑퐁, 메시지마다 받는 쪽 맥락 전체가 다시 읽히는 비용, 같은 논의의 중복.
   - 대책: 작업당 왕복 횟수 상한(예: 3회), 질문은 구체적으로·답은 짧게(안내문 규칙), 팀장에게는 깨우지 않는 요약만 남김, 상한을 넘으면 팀장에게 넘김.
3. **Orca 의존 줄이기:** 핵심은 ddashboard 인박스와 일반 `claude` CLI로만 만듭니다.
   - **팀원은 헤드리스로 실행:** 팀장이 `claude -p`로 팀원을 백그라운드 실행하고, 추가 지시는 `claude -p --resume <세션ID>`로 이어 갑니다. 터미널도 Orca도 필요 없고, 팀원 상태는 대시보드에서 봅니다.
   - Orca는 "팀원 터미널을 눈으로 보고 싶을 때" 쓰는 선택 어댑터로만 둡니다.
   - 헤드리스 팀원의 권한(파일 수정, 명령 실행)은 실행 옵션으로 지정해야 해서 설정 방법을 함께 설계합니다.
4. **모델 등급:** 팀장 상위 모델, 팀원은 역할별 지정(기본은 팀장과 같게). 확정.

## 정해야 할 것 (마스터 결정)

1. **팀원 수명:** 역할별로 오래 유지(저장소를 다시 읽지 않음, 대신 맥락이 커짐) vs 작업마다 새로 띄움(맥락 작음, 대신 매번 읽는 비용). 실험으로 정할지, 기본값을 먼저 정할지.
2. **팀원끼리 직접 대화:** 예를 들어 프론트가 백엔드에게 API를 직접 묻게 할지. 팀장 토큰은 줄지만 팀장이 흐름을 놓칠 수 있습니다. 팀장에게는 깨우지 않는 사본만 남기는 방식이 후보입니다.
3. **팀원 띄우는 방법:** Orca가 있으면 Orca로 자동 실행, 없으면 실행 명령을 안내. 이 방식으로 갈지.
4. **모델 등급:** 팀장은 상위 모델, 팀원은 역할에 따라 하위 모델(예: QA는 가벼운 모델)을 쓸지.

## 진행 순서

1단계(측정)를 먼저 만들고 배포합니다. 그다음 2·3단계를 만들고, 4단계 실험으로 기본값을 정해 0.3.0으로 배포합니다. 1단계만으로도 지금 쓰는 사람들에게 쓸모가 있어서 0.2.x로 먼저 낼 수 있습니다.

## 2단계 상세 설계: 역할·통신·모드 (2026-11-25, 팀장 #002)

원칙: 기존 카드 저장소·인박스·대기 명령을 그대로 재사용합니다. 새 전달 경로는 모두 훅과 스크립트로 처리하고 모델 토큰은 0입니다.

### A. 데이터

| 위치 | 추가 필드 | 의미 |
|---|---|---|
| `projects.json[key]` | `mode` (`solo`/`team`), `lead` (세션 ID), `lead_name`, `mode_ver` (전환할 때마다 +1), `rules` (`{ peer_talk:false, qa_direct:false }`) | 프로젝트 모드와 규칙 |
| `sessions.json[sid]` | `kind` (`lead`/`member`/없음), `role`, `lead`, `headless`, `stay`, `rules_ver` | 세션의 팀 내 위치 |
| 카드 | `via_lead` (팀장 세션 ID) | 팀장에게 보낸 팀원 보고. 본문 피드에서는 숨기고 검색·연구용으로 남깁니다 |
| 인박스 메시지 | `type`: `reply`(마스터 답글) / `report`(팀원→팀장) / `order`(팀장→팀원) | 하나의 인박스로 세 종류를 받습니다 |

### B. 등록

- **팀장:** `/ddashboard:dashboard team <이름>` 명령을 실행하면 `mode=team`, `lead=<이 세션>`으로 설정하고 팀장 안내문을 넣습니다. `/ddashboard:dashboard solo`를 실행하면 solo로 되돌립니다.
- **팀원:** 첫 입력이 `[ddash role=<역할> lead=<팀장 세션 ID> stay=0|1]`로 시작하면, UserPromptSubmit 훅이 `kind=member`로 등록하고 팀원 안내문을 넣습니다. 헤드리스(`claude -p`)에서도 훅은 동작합니다.
- **SessionStart:** team 모드 프로젝트에서는 안내문을 첫 입력 때로 미룹니다. 이 시점에는 태그를 볼 수 없기 때문입니다.
- **태그 없이 들어온 세션(team 모드):** solo처럼 대시보드에 직접 올리고, 사이드바에 "팀 외부"로 표시합니다. → 결정 1

### C. 전달 경로 (Stop 훅·서버·`team.js`)

1. **팀원 카드:** Stop 훅이 카드를 `via_lead`로 저장한 뒤, 팀장 인박스에 `report`를 넣습니다. 보고 내용은 역할, 상태, 제목, 요약, 확인할 것입니다. `details`는 300자를 넘으면 카드 ID만 전달하고, 팀장이 `team.js show <id>`로 읽습니다.
2. **팀장 카드:** 지금처럼 대시보드 본문에 올라갑니다.
3. **마스터 답글:** 팀장 카드에만 달립니다. 팀원 카드는 본문에 없으므로 따로 막을 필요가 없습니다.
4. **팀장 → 팀원 (`team.js send <sid|역할> "지시"`):**
   - 팀원이 대기 중(`wait.lock` 살아 있음)이면 인박스에 `order`를 넣습니다.
   - 대기 중이 아니면(헤드리스 종료 상태) `claude -p --resume <sid>`를 백그라운드로 실행해 이어 갑니다.
5. **팀장 없음:** 팀장 세션이 `ended`이면 팀원 카드를 본문에 직접 올리고 `lead_missing` 경고를 붙입니다.
6. **대기 명령 출력 머리말:** 메시지 종류에 따라 `[Dashboard reply]`, `[Team report]`, `[Lead instruction]` 중 하나를 붙입니다. 팀원 보고가 연달아 오면 한 번에 묶어 받습니다(묶음 대기 시간은 3단계에서 조정).

### D. 팀원 띄우기 (`~/.ddashboard/bin/team.js`, wait.js처럼 경로 고정)

- `team.js spawn --role 프론트 [--model sonnet] [--stay] "과제"`: 태그를 붙여 `claude -p`를 백그라운드로 실행합니다. 로그는 `~/.ddashboard/logs/<sid>.log`에 남기고, 실행 옵션은 세션에 기록합니다(resume할 때 그대로 재사용). Orca가 없어도 됩니다.
- `team.js list`: 팀원 목록(역할, 상태, 대기 여부, 최근 카드)
- `team.js send`, `team.js show`: C항 참고
- **권한 기본값:** `--permission-mode acceptEdits` + `--allowedTools "Bash(git *)" "Bash(node *)" "Bash(npm *)"`. 프로젝트 설정에서 바꿀 수 있습니다. → 결정 3
- **수명:** 기본은 작업이 끝나면 종료(`stay=0`)입니다. `--stay`를 주면 대기 명령을 띄운 채 상주합니다(검증된 동작).

### E. 안내문 (영어, 짧게)

### J. 팀장 교대 자동화 (마스터 추가 요청)

교대할 때 기존 팀장 세션은 **자동으로 종료**합니다.

1. **교대 시작:** 기존 팀장이 인수인계 문서를 쓰고 `team.js handoff <문서 경로>`를 실행합니다.
2. **새 팀장 실행:** 새 팀장을 띄우고, 첫 입력에 `[ddash lead-handoff from=<기존 sid> doc=<경로>]` 태그를 넣습니다. 실행 방법은 헤드리스, 또는 Orca가 있으면 보이는 터미널 중 하나입니다.
3. **팀장 등록:** 새 팀장이 등록되는 순간(UserPromptSubmit 훅) 다음을 처리합니다.
   - `projects.json`의 `lead`를 새 세션으로 바꾸고, 팀원들의 `lead`도 새 세션으로 옮깁니다.
   - 기존 팀장의 인박스에 남은 메시지는 새 팀장 인박스로 옮깁니다.
4. **기존 팀장 종료:**
   - 기존 팀장을 `ended`(교대)로 표시해 needs you를 없앱니다.
   - 대기 명령을 끝내고, SessionStart 때 기록해 둔 Claude 프로세스 PID를 종료합니다.
   - Windows에서 훅의 부모 PID가 실제 claude 프로세스인지는 구현할 때 검증합니다. 프로세스를 끝내지 못하면, 기존 팀장의 다음 턴에 "교대됨, 작업 중지" 안내를 넣는 방식으로 대체합니다.
5. **3단계 연계:** 3단계의 맥락 상한 경고가 이 교대 흐름을 제안합니다.

## K. 그룹 (마스터 제안, 2026-11-26) — 기획과 판정

### 제안 요약
팀장 아래에 **그룹**(예: front)을 둡니다. 그룹을 만들면 `docs/groups/<그룹>/` 폴더가 생기고, 그 그룹의 인수인계 문서는 이 폴더에 씁니다. 대시보드에서는 팀장 아래 그룹이, 그룹 아래 소속 팀원이 붙습니다. 그룹은 만들기·수정·삭제할 수 있고, 팀장이 그룹을 관리하며 특정 그룹에 팀원을 파견합니다.

### 판정: 채택 권장 (범위를 줄인 MVP로)

**얻는 것**
1. **연속성:** 그룹 폴더가 그룹의 기억이 됩니다. 팀원을 작업마다 새로 띄워도(stay 꺼짐, 맥락 작음) 다음 팀원이 brief와 handoff로 이어 받습니다. 결정을 미뤄 둔 "팀원 수명" 문제의 답이 됩니다.
2. **탐색 비용 절감:** 그룹 brief에 담당 범위와 관련 파일을 적어 두면 팀원이 저장소를 훑지 않습니다. 이번 구현 팀원은 약 20만 토큰을 썼는데, 그중 상당 부분이 코드 파악이었습니다.
3. **화면 정리:** 팀원이 늘어도 사이드바가 그룹 단위로 묶입니다.
4. **파견 단위가 명확해짐:** 팀장은 "front에 맡긴다"라고만 정하면 되고, 맥락은 그룹 폴더가 공급합니다.

**위험과 대책**

| 위험 | 내용 | 대책 |
|---|---|---|
| 캐시 공유는 기대보다 작음 | 프롬프트 캐시는 앞부분이 글자 하나까지 같아야 공유됩니다. 시스템 프롬프트에 cwd와 git status가 들어가므로, 다른 worktree에 있거나 커밋 사이에 띄운 팀원끼리는 공유되지 않습니다. 팀원이 Read 도구로 brief를 읽으면 과제 문장 뒤에 들어가서 더더욱 공유되지 않습니다 | brief를 훅이 과제보다 앞에 넣도록 하고, 크기는 4천 토큰 이하로 둡니다. 실제 캐시 적중은 4단계에서 측정합니다. **캐시 절감은 덤으로 보고, 주된 이득은 연속성과 탐색 절감입니다** |
| 브랜치마다 문서가 갈림 | 팀원이 자기 feature 브랜치에 handoff를 쓰면, 병합 전에는 다른 팀원에게 보이지 않습니다 | 그룹 폴더는 **팀장 worktree 한 곳**에만 둡니다. 팀원은 절대 경로로 읽고 쓰고, 커밋은 팀장이 docs 커밋으로 모아서 합니다 |
| brief가 낡음 | 코드는 바뀌었는데 brief는 옛 내용 그대로 | handoff를 쓸 때 brief도 갱신하는 것을 규칙으로 둡니다. git HEAD가 많이 앞서면 갱신 필요 경고를 띄웁니다(3단계) |
| 기능이 겹침 | role과 group이 비슷해 혼란 | group을 주 단위로, role은 선택 사항(그룹 안의 세부 역할)으로 둡니다 |
| 과잉 설계 | 4단계 실험 전에 구조를 너무 키움 | MVP만 0.3.0에 넣습니다. 그룹장과 그룹별 묶음 보고는 실험 이후로 미룹니다 |

### MVP 범위 (0.3.0)
- **데이터:** `projects.json[key].groups[이름] = { dir, created }`, 세션에는 `group`을 기록합니다.
- **명령:** `T group create|rename|delete <이름>`, `T spawn --group <이름> "과제"`, `T group list`
- **폴더:** 그룹을 만들면 `docs/groups/<이름>/brief.md`(템플릿)를 생성합니다. handoff는 `handoff-NNN.md`, 보고 근거는 `notes/`에 둡니다.
- **새 팀원 시작:** 훅이 brief 전문과 최신 handoff 경로를 과제보다 앞에 넣습니다.
- **그룹 팀원의 마무리:** 끝날 때 해당 그룹 폴더에 handoff를 쓰라는 규칙을 안내문에 넣습니다.
- **화면:** 팀장 → 그룹 → 팀원 순으로 표시합니다. 그룹마다 + member, 그룹 만들기·이름 바꾸기·지우기, 그룹 없는 팀원은 "unassigned"로 둡니다.
- **이름 바꾸기:** 폴더도 함께 옮기고(`git mv`), 소속 세션의 `group` 값도 바꿉니다.

**이후로 미룸:** 그룹장(중간 팀장), 그룹별 묶음 보고, brief 자동 갱신 경고

### 마스터 결정 요청
1. **그룹 폴더 git 커밋:** 추천은 커밋입니다(팀장이 docs 커밋으로 모아서 함). 대안은 .gitignore 처리입니다.
2. **그룹 삭제:** 추천은 대시보드에서 없애고 팀원을 unassigned로 옮기며, 폴더는 `docs/groups/_archived/`로 옮기는 것입니다. 대안은 폴더까지 삭제하는 것입니다.
3. **그룹장:** 추천은 지금은 두지 않고 4단계 실험 후보로 남기는 것입니다.
4. **brief 주입 방식:** 추천은 훅이 과제 앞에 넣는 것입니다(캐시와 일관성에 유리, 4천 토큰 상한). 대안은 팀원이 직접 파일을 읽는 것입니다(단순하지만 캐시 공유 없음).
5. **팀 모드에서 그룹을 필수로 할지:** 추천은 선택입니다(그룹 없이 띄우면 unassigned). 대안은 필수입니다.
6. **위치:** 추천은 `docs/groups/` 고정입니다. 대안은 프로젝트별로 경로를 설정할 수 있게 하는 것입니다.

### K-2. docs 크기 관리 (판정)
- **문서가 커져도 토큰은 늘지 않습니다.** 토큰 비용은 디스크에 쌓인 양이 아니라 실제로 읽는 양에서 생깁니다. 팀원은 brief와 최신 handoff만 읽으므로, 옛 문서가 쌓여도 토큰은 늘지 않습니다.
- **실제 위험은 세 가지입니다.**
  1. brief가 계속 길어지는 것: 매번 주입되므로 비용이 커집니다.
  2. 팀원이 grep이나 glob으로 검색할 때 옛 문서가 걸려 잡음이 되는 것
  3. 저장소가 지저분해 보이는 것
- **대책:** 주기적으로 비우는 대신 **쓸 때 자동으로 정리**합니다.
  1. **handoff 교체:** 새 handoff를 쓰면 그룹 폴더에는 최신 3개만 남기고, 나머지는 작업 트리에서 지웁니다. git 기록에는 남으므로 필요하면 `git log`로 꺼낼 수 있습니다.
  2. **notes 정리:** `notes/`에서 30일이 지난 파일은 같은 방식으로 지웁니다.
  3. **brief 상한:** 4천 토큰을 넘으면 넣을 때 잘라 내고, 팀장에게 "brief 정리 필요"를 알립니다.
  4. **수동 정리:** `T group prune [<이름>]`으로 직접 정리할 수 있습니다. 정리 결과는 팀장이 docs 커밋으로 모아서 커밋합니다.
- **설정값:** 남길 handoff 개수와 notes 보관 일수는 `projects.json`의 그룹 설정으로 바꿀 수 있습니다(기본 3개, 30일).
