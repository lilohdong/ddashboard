# ddashboard 0.3.0 계획: 대시보드로 꾸리는 개발 팀

## 목표

- **마스터(사용자)는 팀장하고만 협업**합니다. 팀장은 여러 명일 수 있습니다.
- **팀원 세션은 역할을 맡습니다.** 예: 기획, 프론트, 백엔드, QA.
- 팀원은 작업이 끝나면 **팀장에게 보고**합니다.
- 팀장은 특이사항, 수정사항, 마스터가 알아야 할 것, 검수 요청만 **대시보드에 올립니다.**
- **토큰 사용량을 측정하면서 설계를 정합니다.** 추측으로 정하지 않습니다.

## 핵심 원칙 (지금까지 배운 것)

1. **비용은 "깨우는 횟수 × 깨어난 세션의 맥락 크기"로 정해집니다.** 0.1.0 분석에서 팀장 맥락이 턴당 평균 37.5만 토큰이었고, 이것이 비용의 대부분이었습니다.
2. **전달 자체는 공짜로 만들 수 있습니다.** 파일 인박스와 대기 명령은 토큰 0입니다. 그래서 줄여야 할 것은 "누가, 몇 번, 얼마나 큰 맥락으로 깨어나는가"입니다.
3. **작은 일은 팀장이 직접, 큰 일만 분배합니다.** 팀원을 새로 띄우면 저장소를 다시 읽는 비용이 붙습니다.

## 단계별 계획

### 1단계: 측정 도구 (연구의 바탕)

토큰을 재지 않으면 연구가 안 되므로 가장 먼저 만듭니다.

- **세션별 토큰 미터:** Stop 훅이 transcript 끝부분에서 이번 턴의 사용량(입력, 캐시 읽기, 캐시 쓰기, 출력)을 읽어 기록합니다. 모델 토큰은 0입니다.
- **깨운 원인 기록:** 사람 입력, 대시보드 답글, 팀원 보고, 팀장 지시 중 무엇 때문에 깨어났는지 함께 기록합니다.
- **대시보드 표시:** 사이드바 세션마다 누적 토큰과 최근 맥락 크기를 표시하고, 팀 전체 합계를 보여 줍니다. 맥락이 커지면 경고합니다.

### 2단계: 역할과 통신

- **팀장 등록:** `/ddashboard:dashboard lead 백엔드팀장` 처럼 이름을 붙여 켭니다.
- **팀원 등록:** 팀장이 팀원을 띄울 때 지시문 첫 줄에 `[ddash role=프론트 lead=<팀장 세션 ID>]` 태그를 넣으면, 첫 입력 때 훅이 소속과 역할을 등록합니다. Orca를 쓰든 터미널에 직접 붙여 넣든 동작합니다.
- **통신은 ddashboard 인박스로 통일합니다.** Orca 없이도 동작하고 토큰 0입니다.
  - 팀장 → 팀원: 팀원 인박스에 지시를 넣습니다.
  - 팀원 → 팀장: 팀원의 카드는 대시보드 본문이 아니라 팀장 인박스로 갑니다.
  - 팀장 → 대시보드: 팀장 카드만 본문에 올라갑니다.
  - 마스터 답글: 팀장 카드에만 달 수 있고, 팀장에게 갑니다.
- **화면:** 사이드바에 팀장 아래로 팀원이 역할과 함께 들여쓰기로 표시됩니다. 팀원 보고는 팀장 카드 안에 접어서 볼 수 있습니다.

### 3단계: 팀장 비용을 줄이는 장치

- **보고 묶어 받기:** 팀원 보고가 연달아 오면 몇 초 기다렸다가 한 번에 받습니다. 깨우는 횟수가 줄어듭니다.
- **보고는 짧게, 근거는 파일로:** 보고는 카드 JSON(요약 3줄, 확인할 것)만 보냅니다. 긴 내용은 파일로 남기고 경로만 전달해서, 팀장이 필요할 때만 읽게 합니다.
- **팀장 맥락 상한과 교대:** 맥락이 일정 크기(예: 15만 토큰)를 넘으면 팀장이 인수인계 문서를 쓰고 새 팀장 세션으로 교대합니다. 1단계 미터가 신호를 줍니다.
- **작업 키:** 카드에 작업 이름(key)을 붙이고, 같은 key의 새 카드가 오면 이전 카드를 대체합니다. 진행 중 카드가 완료 카드로 자연스럽게 바뀝니다.
- **카드 언어 설정:** 프로젝트별로 카드 언어를 정합니다. 팀원에게 영어로 지시해도 카드는 마스터의 언어로 나옵니다.
- **응답 없는 세션 표시:** 대기 명령도 없고 오래 조용한 세션은 "응답 없음"으로 표시합니다.

### 4단계: 실험

같은 과제를 세 가지 방식으로 돌려 토큰, 걸린 시간, 결과 품질을 비교합니다.

| 방식 | 내용 |
|---|---|
| A. 혼자 | 세션 하나가 전부 처리 |
| B. 직접 보고 | 여러 세션이 각자 대시보드에 보고 (0.2.0 방식) |
| C. 팀장 경유 | 팀장 + 역할 팀원, 보고는 팀장에게 (0.3.0 방식) |

과제는 이 저장소의 실제 기능 하나로 정합니다. 결과로 기본값(보고 묶음 시간, 맥락 상한, 팀원 모델 등급)을 정하고, 문서로 남깁니다.

## 모드: solo / team (자유도를 지키는 구조)

도구는 장치만 제공하고, 일하는 방식은 사용자가 고릅니다. 개발론은 강제하지 않고 team 모드의 기본값과 README의 안내로 제공합니다.

| | solo (기본) | team |
|---|---|---|
| 켜는 법 | `/ddashboard:dashboard` | `/ddashboard:dashboard team <팀장 이름>` |
| 누가 대시보드에 올리나 | 연결된 모든 세션 (0.2.0과 같음) | 팀장만. 팀원 카드는 팀장 인박스로 |
| 마스터 답글 | 카드를 올린 세션으로 | 팀장에게 |
| 팀원 등록 | 없음 | 팀장이 띄울 때 태그로 소속·역할 등록 |
| 규칙 조정 | — | 프로젝트 설정 파일에서 규칙별로 켜고 끔 (예: QA 카드는 직접 게시, 팀원끼리 대화 허용) |

- 모드는 프로젝트마다 다르게 둘 수 있고, 언제든 바꿀 수 있습니다.
- **전환 방법은 두 가지 모두 지원합니다(확정).** 명령어(`/ddashboard:dashboard team <팀장 이름>` / `solo`)와 대시보드 화면(사이드바 프로젝트 이름 옆 solo/team 전환, team 선택 시 팀장 세션 고르기).
- 전달 경로는 전환 즉시 바뀝니다(훅·서버 처리, 토큰 0). 세션 안내문은 다음 입력 때 한 번만 새 모드로 다시 넣습니다.
- team 모드에서 팀장이 종료되면 팀원 카드는 대시보드에 직접 올리고 "팀장 없음" 경고를 표시합니다.
- README에 두 모드의 사용법을 나눠 안내하고, team 모드의 권장 방식(개발론)은 별도 가이드 문서로 링크합니다.

## 마스터 피드백 반영 (2026-11-25)

1. **저장소 압축(프로젝트 브리프):** 팀원이 매번 저장소를 탐색하지 않도록, 팀장이 `프로젝트 브리프`(구조, 파일별 한 줄 설명, 규칙, 현재 작업 상태)를 만들어 둡니다.
   - 팀원은 탐색 대신 브리프를 읽고 필요한 파일만 엽니다. 탐색 수만 토큰 → 브리프 수천 토큰.
   - **브리프를 모든 팀원 맥락의 같은 위치에 같은 내용으로 넣으면 프롬프트 캐시가 세션 사이에서 공유됩니다.** 두 번째 팀원부터는 브리프 비용이 캐시 읽기(약 1/10)로 떨어집니다.
   - git HEAD가 브리프 작성 시점보다 많이 앞서면 훅이 "브리프 갱신 필요"를 팀장에게 알립니다.
   - 팀원 수명은 "작업마다 새로 + 브리프"를 기본으로 하고, 실험에서 "역할별 유지 + 맥락 상한"과 비교합니다.
2. **팀원끼리 직접 대화의 낭비 위험:** 두 세션이 끝없이 주고받는 핑퐁, 메시지마다 받는 쪽 맥락 전체가 다시 읽히는 비용, 같은 논의의 중복.
   - 대책: 작업당 왕복 횟수 상한(예: 3회), 질문은 구체적으로·답은 짧게(안내문 규칙), 팀장에게는 깨우지 않는 요약만 남김, 상한을 넘으면 팀장에게 넘김.
3. **Orca 의존 줄이기:** 핵심은 ddashboard 인박스와 일반 `claude` CLI로만 만듭니다.
   - **팀원은 헤드리스로 실행:** 팀장이 `claude -p`로 팀원을 백그라운드 실행하고, 추가 지시는 `claude -p --resume <세션ID>`로 이어 갑니다. 터미널도 Orca도 필요 없고, 팀원 상태는 대시보드에서 봅니다.
   - Orca는 "팀원 터미널을 눈으로 보고 싶을 때" 쓰는 선택 어댑터로만 둡니다.
   - 헤드리스 팀원의 권한(파일 수정, 명령 실행)은 실행 옵션으로 지정해야 해서 설정 방법을 함께 설계합니다.
4. **모델 등급:** 팀장 상위 모델, 팀원은 역할별 지정(기본은 팀장과 같게). 확정.

## 정해야 할 것 (마스터 결정)

1. **팀원 수명:** 역할별로 오래 유지(저장소를 다시 읽지 않음, 대신 맥락이 커짐) vs 작업마다 새로 띄움(맥락 작음, 대신 매번 읽는 비용). 실험으로 정할지, 기본값을 먼저 정할지.
2. **팀원끼리 직접 대화:** 예를 들어 프론트가 백엔드에게 API를 직접 묻게 할지. 팀장 토큰은 줄지만 팀장이 흐름을 놓칠 수 있습니다. 팀장에게는 깨우지 않는 사본만 남기는 방식이 후보입니다.
3. **팀원 띄우는 방법:** Orca가 있으면 Orca로 자동 실행, 없으면 실행 명령을 안내. 이 방식으로 갈지.
4. **모델 등급:** 팀장은 상위 모델, 팀원은 역할에 따라 하위 모델(예: QA는 가벼운 모델)을 쓸지.

## 진행 순서

1단계(측정)를 먼저 만들고 배포합니다. 그다음 2·3단계를 만들고, 4단계 실험으로 기본값을 정해 0.3.0으로 배포합니다. 1단계만으로도 지금 쓰는 사람들에게 쓸모가 있어서 0.2.x로 먼저 낼 수 있습니다.
