# 연구 기록: 팀장 교대 #001과 자동화 가능성

## 1. 교대 직전 측정 (이전 팀장 `d0504315`)

| 항목 | 값 |
|---|---|
| 모델 턴 | 302 |
| 캐시 읽기 누적 | 92,318,091 |
| 캐시 쓰기 누적 | 1,016,664 |
| 출력 누적 | 306,617 |
| 현재 맥락 | 506,915 |
| 최근 20턴 평균 맥락 | 499,513 |
| 자동 요약(compaction) | 0회 |

이 시점에서는 카드 답글 하나를 처리하는 데 매 턴 약 50만 토큰을 캐시로 다시 읽었다.

## 2. 교대 비용과 손익분기 (추정)

가중치는 상대 비교용 가정이다: 캐시 읽기 0.1, 캐시 쓰기 1.25, 출력 5 (입력 1 기준).

| 항목 | 추정 |
|---|---|
| 이전 팀장 턴당 비용 | 50만 × 0.1 = 약 5만 |
| 새 팀장 턴당 비용 (맥락 약 4만으로 시작) | 4만 × 0.1 = 약 0.4만 (이후 서서히 증가) |
| 턴당 절감 | 약 4.6만 |
| 교대 1회 비용 | 인수인계 문서 작성(출력 약 0.6만 × 5 = 3만) + 이전 팀장의 작성 턴(5만) + 새 팀장 시작 캐시 쓰기(4만 × 1.25 = 5만) = 약 13만 |
| **손익분기** | **약 3턴** |

결론: 맥락이 수십만 토큰까지 커진 팀장은 교대하는 쪽이 압도적으로 싸다. 상한을 15만 정도로 잡아도 손익분기는 10턴 안쪽이다.

새 팀장의 실제 시작 맥락과 이후 턴당 맥락은 교대 후 측정해 이 문서에 추가한다.

## 3. 플러그인 안에서 자동화할 수 있는가

**가능하다.** 필요한 부품이 대부분 이미 있다.

| 단계 | 방법 | 모델 토큰 |
|---|---|---|
| 1. 상한 감지 | Stop 훅이 턴별 맥락 크기를 기록(1단계 토큰 미터). `DDASH_LEAD_CTX_CAP`(예: 15만)을 넘으면 표시 | 0 |
| 2. 인수인계 요청 | Stop 훅이 `decision: block`으로 "지정 경로에 인수인계 문서를 쓰고 끝내라"를 넘김 | 문서 작성 1턴 |
| 3. 새 팀장 실행 | 헤드리스 `claude -p "인수인계 문서를 읽고 팀장 업무를 이어라"` (검증됨: 헤드리스 세션도 인박스 답글로 깨어남). Orca가 있으면 보이는 터미널로 실행하는 선택지 | 새 세션 시작 비용 |
| 4. 역할 이전 | projects.json의 팀장 세션 ID를 새 세션으로 바꿈. 팀원 보고와 마스터 답글은 세션 ID가 아니라 "팀장" 역할로 보내고 전달 시점에 해석 | 0 |
| 5. 이전 팀장 정리 | 이전 세션에 "교대 완료, 대기 명령을 다시 띄우지 말 것"을 보내고 종료 표시 | 1턴 |

### 고려할 점

- **인수인계 품질:** 문서가 부실하면 새 팀장이 다시 묻거나 저장소를 탐색해 비용이 늘어난다. 인수인계 문서 틀(이 문서의 목차)을 플러그인이 제공하면 품질이 안정된다.
- **헤드리스 팀장의 한계:** 마스터가 팀장 터미널을 보지 못하고 대시보드로만 소통한다. 권한은 실행 옵션으로 미리 정해야 한다.
- **진행 중인 메시지:** 교대 중에 온 팀원 보고가 이전 팀장에게 가지 않도록, 역할 기반 전달(4번)이 필요하다.
- **Claude Code 자동 요약과 비교:** 기본 자동 요약은 맥락 창이 거의 찰 때 동작해서(맥락 창이 크면 아주 늦게 동작) 그 전까지 비싼 턴이 계속된다. 우리 상한은 더 이르고, 인수인계 문서가 남아 사람도 읽을 수 있다.
